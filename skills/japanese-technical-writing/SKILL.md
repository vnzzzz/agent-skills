# 日本語技術文書

技術文書では、読者が仕様、判断理由、条件、手順を読み違えないことを優先する。
読み物としての演出より、何が事実で、どの条件で成立し、どこに例外や制約があるかを明確にする。

このSkillはrepository非依存の共通原則だけを定める。
より具体的なrepository-localの用語、文書配置、実行環境、正本の分担、product固有規則がある場合は、それらを優先する。

## 文と段落

- 一文ごとに改行する。
- 段落は空行で区切る。
- 一つの段落では一つの論点だけを扱う。
- 段落の先頭で、扱う対象か直前の段落との関係が分かるようにする。
- 「本節では」「次に説明する」など、文書の進行だけを述べる文は置かない。
- 根拠がある内容は具体的に書き、未確認の内容には不確実性を残す。
- 原因と結果を書く場合は、なぜその結果になるのかを示す。

短くするために条件や例外を削らない。
長い一文へ複数の条件や結論を詰め込まず、必要なら段落、箇条書き、表へ分ける。

## 用語

同じ概念には同じ用語を使う。
一度定義した用語を、文章上の変化だけを目的に似た別語へ置き換えない。

分野で一般的な用語を優先する。
英語を直訳しただけで意味が伝わりにくい日本語や、説明なしでは解釈しにくい抽象語を避ける。

コード上の識別子、API項目名、設定キー、列挙値、コマンド名は勝手に翻訳または言い換えない。
本文では、それらが何を表すかを自然な日本語で説明する。

固有概念を初めて使う場合は、その場で意味を説明する。
強調は初出の定義や誤読を防ぐ箇所に限定する。

## 仕様の重複

一つの仕様は、最も関係の深い正本に詳しく記載する。
別の文書で同じ仕様に触れる場合は、必要な要点だけを書き、正本を参照する。

README、索引、概要文書へ詳細な仕様や手順を複製しない。
同じコマンド手順、設定値、制約を複数の文書で独立に保守しない。

生成物について説明する場合は、正本と生成方法を区別する。
同じ内容を図、表、本文へ重複して書かない。

文書を分割する場合は、それぞれの責務を重ねない。
共有する必要がある情報は、複製ではなく参照でつなぐ。

## 事実と不確実性

次を区別して書く。

- 確認済みの事実
- 設計または仕様として決めた内容
- 推測や仮説
- 例外
- 前提条件
- 制約や処理上限
- 例が示す範囲

推測を事実のように断定しない。
一部だけ確認した結果を、全体を確認した結果として書かない。

処理上限や打切りがある場合は、上限値だけでなく、到達時に結果をどう扱うかを書く。
例が仕様の一部だけを示す場合は、その範囲を明記する。

## 文書種別

文書の目的に応じて構成を変える。

| 文書種別 | 構成の基本 |
|---|---|
| API仕様 | 入出力、条件、例外、エラーを直接記載する |
| 運用手順 | 前提、実行条件、操作、確認結果を順に記載する |
| 開発手順 | 作業条件と再現可能な手順を直接記載する |
| 技術解説 | 読者の前提を示し、概念、理由、具体例の関係が追えるようにする |
| チュートリアル | 読者の前提と達成する目的を示し、操作とその理由を対応させる |
| 設計背景 | 状況、制約、選択肢、判断理由、結果の順序が追えるようにする |

API仕様や手順へ、結論に不要な物語的展開、比喩、読み物向けの演出を追加しない。
技術解説やチュートリアルでは、理解を助ける場合に限って導入や具体例を使う。

## 図、表、コードブロック

文章より関係を短く正確に示せる場合に図や表を使う。
装飾のためには追加しない。

- 順序や分岐はフロー図が適する。
- 複数の対象の比較や対応関係は表が適する。
- コマンド、設定、JSON、HTTPメッセージ、ログ、ファイル構成はコードブロックが適する。
- 長い説明文や手順を一つの表セルへ詰め込まない。

図や表の本文では、図表だけでは分からない条件、例外、判断規則を補う。
図表が示している情報をそのまま文章で繰り返さない。

## 表記

- 見出しは、その節で扱う対象が分かる短い名詞句を基本とする。
- 一つの見出しへ複数の論点を詰め込まない。
- 日本語の並列は読点または箇条書きを使い、記号だけで関係を曖昧にしない。
- 定義の一覧は、項目が少なければ簡潔な列挙、比較が必要なら表を使う。
- 本文の流れを止める長い補足は別段落または別節へ分ける。

repository-localの表記規則がある場合は、その規則を優先する。

## 推敲

執筆後に次を確認する。

- 各文が、事実、仕様、判断理由、条件、手順のいずれかを新しく伝えているか。
- 一文と一段落に複数の論点を詰め込んでいないか。
- 同じ概念に同じ用語を使っているか。
- 識別子や公開名を誤って翻訳または変更していないか。
- 別の正本にある仕様を複製していないか。
- 事実、推測、例外、前提、制約、上限を区別しているか。
- 例が示す範囲を仕様全体と誤認させないか。
- 文書種別に不要な導入、比喩、進行説明を残していないか。
- 図、表、本文で同じ情報を重複していないか。
- repository-localの用語、配置、正本、運用規則と矛盾していないか。

長い断定文が続く場合は、比較を表、順序や分岐を図、具体的な形式をコードブロックへ分けられないか確認する。
ただし、形式を変えるために必要な条件や例外を削らない。
