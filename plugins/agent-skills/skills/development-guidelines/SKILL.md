# Development Guidelines

現在確認できている要件を満たす、最も単純で明示的な実装から始める。
短いコードを目的にするのではなく、理解・変更・検証すべき概念を必要以上に増やさない。

## まず既存実装を使う

新しい仕組みを追加する前に、関連コードと既存の責務分担を確認する。

次の順で検討する。

1. 変更しなくても既存機能の使い方で解決できないか
2. 既存実装の小さな修正や削除で解決できないか
3. 既存componentの責務を自然に拡張できないか
4. それでも責務が異なる場合だけ新しい実装を追加する

新しいfile、class、interface、wrapper、factory、registry、configurationを初期解にしない。
既存patternが適切なら再利用するが、既存の複雑さを理由なく複製しない。

## 現在必要なものだけを実装する

将来の可能性だけを理由にgeneric化、抽象化、設定可能化しない。

避ける例:

- backendが増えるかもしれないという理由だけでinterfaceやfactoryを追加する
- 利用者のいない値をconfiguration化する
- 1種類しかない処理へstrategyやplugin機構を導入する
- 再利用予定のない処理を再利用性だけのためにlayerへ分離する
- 「柔軟性」「拡張性」「将来性」だけを追加理由にする

将来の要件は、実際の形と制約が分かってから解く。

## 最小実装と手抜きを区別する

単純化を理由に、成立に必要な品質を省略しない。

必要に応じて必ず扱うもの:

- 公開契約として必要な入力検証
- data corruptionやsecurity issueを防ぐ処理
- 実際に発生し得るfailureへのerror handling
- resource lifecycle、concurrency、transaction等の安全性
- 変更リスクに対応する検証
- codeだけでは失われる制約や判断理由

不要な機能を作らないことと、必要なfailure modeを無視することは別である。

## 後方互換性は要件として扱う

後方互換性は、公開契約・外部consumer・永続data・migration・実際の利用実態など、維持すべき理由がある場合だけ担保する。

- 「念のため」旧API、旧設定名、旧path、deprecated wrapperを残さない
- callerを同じ変更で安全に移行できるなら不要なcompatibility layerを追加しない
- 互換性が必要なら、何との互換性をなぜ維持するかを明確にする
- 互換性を外す場合も、外部影響やmigrationの必要性を確認する

過去の実装が存在したという事実だけを互換性要件にしない。

## 変更を小さく保つ

1つの変更では1つの目的に集中する。

- 機能変更と無関係なcleanupや大規模reformatを混ぜない
- 大きな変更は、各段階でsystemが成立する自己完結した変更へ分割する
- 変更量ではなく、reviewerが1つの目的として理解・検証できるかで境界を決める
- 分割のためだけに一時的な不要architectureを作らない

## 複雑さを追加するときの基準

新しいabstractionやlayerを追加する場合、現在の要件に基づいて存在理由を説明できることを確認する。

有効な理由の例:

- 明確に異なる複数実装が既に存在する
- external contractとの境界を隔離する必要がある
- security、transaction、resource ownership等の責務を分離する必要がある
- 重複したdomain ruleを1か所に集約する必要がある

「きれいに見える」「一般的なpatternだから」は単独では理由にしない。

## 実装中の判断

要件外の問題を見つけても、現在の変更へ無条件に混ぜない。

- 今回の変更を安全に成立させるため必須なら同じscopeで扱う
- 独立して修正できるなら別変更へ分ける
- 修正価値が低いものは、見つけたという理由だけで直さない

局所最適だけでなくsystem全体のcode healthは見るが、1つの変更で全体を作り直そうとしない。

## 完了時の確認

実装後に次を確認する。

- 要件にない機能・設定・抽象化が増えていないか
- 追加した各function / class / layerの存在理由を現在の要件で説明できるか
- 既存実装の修正で済むのに重複した仕組みを作っていないか
- 不要なcompatibility codeを残していないか
- 必要なvalidation、failure handling、安全性を省略していないか
- より単純な構造で同じ契約を満たせないか
- 無関係な変更を混ぜていないか

コードは完璧である必要はない。変更前よりcode healthを悪化させず、現在の問題を十分に解決することを優先する。

## 他Skillとの関係

- そもそも何を解決すべきか、solutionがuser needに合うかは `product-thinking` を利用する。
- 命名や関数分割でも残らない判断理由・制約・不変条件をcommentへ残す場合は `code-comments` を利用する。

このSkillは、product requirement、testing methodology、documentation styleそのものを定義しない。
