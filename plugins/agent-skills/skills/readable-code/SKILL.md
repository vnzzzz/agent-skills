# Readable Code

コメントを追加する前に、役割が分かる名前を付け、処理のまとまりが分かる関数へ分ける。
命名と関数分割を行ってもコードだけでは伝わらない判断理由、制約、不変条件をコメントで補う。

コメント量そのものを品質指標にしない。
コメントがなくても意図が明確なコードを優先し、コードだけでは将来の変更時に失われる知識だけを残す。

## コメントする対象

- 公開関数、型、定数の役割と、呼出側が守る条件
- 非自明なアルゴリズムやデータ変換を選んだ理由
- 処理中と処理後に維持する不変条件
- 並行処理における値や資源の所有権、ロック範囲、終了条件
- 設定、接続、ファイル、キャッシュなどの資源を切り替える条件と、旧資源を破棄できる条件
- 入力検査が防ぐデータ破損、資源枯渇、曖昧な解釈
- 正規化で同一視する値と、区別したまま扱う値
- 互換性を維持するために残している処理と、維持する互換性
- 処理上限と、その上限が必要な理由、上限到達時の扱い
- Workaroundが必要になった原因と、削除できる条件

## コメントしない対象

- コードの処理をそのまま自然言語で言い換えた説明
- 変数名や関数名だけで明らかな内容
- 将来必要になるかもしれないという理由だけで追加した設計
- Issue番号や外部リンクを確認しなければ意味が分からない説明
- 生成ファイルへの手書きコメント
- formatter、linter、style guideで機械的に決めるべき事項

既存コードへ一括でコメントを追加しない。
変更する処理とその周辺だけを読み、必要な箇所を改善する。

コメント率やコメント行数などの数値目標は設けない。
コメントの要否は、コードだけでは判断理由、制約、不変条件を維持できるかで決める。

## 例

以下はGoで示すが、判断基準は言語に依存しない。

### 資源の切替

操作名ではなく、切替条件と資源の寿命を説明する。

```go
// よくない例：現在の資源を切り替える。
old := current.Swap(next)
old.CloseWhenIdle()

// 良い例：検査済みの新しい資源を先に公開し、切替前に開始した処理は旧資源を参照できる状態を保つ。
old := current.Swap(next)
// 旧資源は参照中の処理がなくなった後だけ閉じる。
old.CloseWhenIdle()
```

### 入力検査

検査内容ではなく、検査が防ぐ問題を説明する。

```go
// よくない例：入力サイズを確認する。
body := http.MaxBytesReader(w, r.Body, maxBodySize)

// 良い例：過大入力を後続のデコード処理へ渡さず、受信中にメモリ使用量を制限する。
body := http.MaxBytesReader(w, r.Body, maxBodySize)
```

### 正規化

何を同一視し、何を区別するかを明示する。

```go
// よくない例：識別子を正規化する。
normalized := normalizeIdentifier(value)

// 良い例：Unicode互換文字と前後空白は同一視するが、大文字と小文字は区別する。
normalized := normalizeIdentifier(value)
```

### 処理上限

値そのものではなく、上限の理由と到達時の契約上の振る舞いを説明する。
上限到達時にエラー、部分結果、再試行などのどの挙動を採用するかはこのSkillでは決めず、実際の契約に合わせる。

```go
// よくない例：最大件数。
const maxResults = 1_000

// 良い例：公開APIの契約上、1,000件を超える要求はLimitExceededとして拒否する。
const maxResults = 1_000
```

## レビュー

実装を変更した場合は、同じ変更で関連するコメントを更新する。
差分レビューでは、コメントが説明する理由、制約、不変条件と実装が一致していることを確認する。
実装から確認できない古い説明は残さず、現在の条件に合わせて修正または削除する。

コメントを追加することで複雑さを隠している場合は、先に命名、関数分割、データ構造、制御フローを改善できないか確認する。
