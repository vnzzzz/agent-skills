# README Writing

READMEはrepositoryの入口である。読者が「何ができるか」「自分に役立つか」「どう始めるか」を短時間で判断できるようにする。短さ自体ではなく、必要な情報に迷わず到達できることを優先する。

## 1. 読者と現状を確認する

- 対象読者、利用目的、最初に成功させたい操作を特定する。
- 既存READMEとrepositoryのmanifest、entry point、公開interface、docs、CI、LICENSE等を確認する。
- 記載するcommand、option、version、機能、利用条件が現在の実装や正本と一致するか確かめる。推測で補わない。
- Repository固有の文書構成、言語の正本・翻訳、生成section等の規約を優先する。

## 2. 説明する順序を決める

原則として次の順に、存在する情報だけを置く。

1. **Project名と一文の価値** — 誰に何を提供するかを具体的に伝える。
2. **Quick Start** — 最短のinstall / setupと、動作を確認できる実例を示す。
3. **主な機能・使い方** — 価値を判断するのに必要なものだけを示す。
4. **詳細への導線** — 詳しい仕様、設定、運用、貢献方法は正本へリンクする。

小さなrepositoryでは章を減らしてよい。READMEを仕様書、変更履歴、API一覧、設計書の複製先にしない。

## 3. 簡潔に、見やすくする

- 冒頭の説明を抽象的な宣伝文句にせず、対象読者と利用価値が伝わる短い文にする。初見の読者が何を頼めるか分かる実例を優先する。
- 短い見出しと段落、コピー可能なcode block、必要な場合だけ表や画像を使う。
- 同じ説明を本文、表、例に重複させない。自明な見出しや定型章を増やさない。
- Badgeは付けないことを初期値とする。読者の選択に実際に役立つ場合だけ追加し、出所・値・リンク先を検証する。CI passing等、重要性が低い状態表示で冒頭を埋めない。
- 視覚的な魅力は、情報の優先順位、余白、具体的な例でつくる。Logoやスクリーンショットは機能や体験の理解に役立つ場合だけ使い、装飾で埋めない。

## 4. 更新を検証する

- Commandと例を安全に実行できる場合は試し、できない場合は未検証と明記する。
- Relative link、badge URL、target file、生成marker等が壊れていないことを確認する。
- READMEが複数言語で管理される場合は正本・翻訳を同じ変更で同期する。
- 実装とREADMEの不一致が見つかっても、文書に合わせるためだけに実装を変更しない。必要なら別の変更として提案する。
- 最終報告は改善点と実施した検証に絞る。

## 他Skillとの関係

- `technical-writing`: README以外の仕様、設計、運用手順、技術解説を担当する。
- このSkillはREADMEの情報選択・構成・見せ方を扱う。Repository固有の規則や内容の正本は上書きしない。
