# Testing

テストは、実装量やテストケース数を増やすためではなく、利用者やシステムにとって重要な振る舞いが守られていることを検証するために書く。

テストが失敗したときに「重要な何かが壊れた」と判断できることを重視する。
実装詳細へ過剰に結合し、無害なリファクタリングだけで失敗するテストを増やさない。

このSkillはrepository非依存のテスト設計原則を扱う。
具体的なtest command、framework、directory構成、CI規則がある場合はrepository-localの規則を優先する。

## 最初に確認すること

テストを追加する前に、次を明確にする。

- 今回守るべき利用者またはシステムの振る舞いは何か。
- public contract、重要なinvariant、失敗条件のどれを検証するのか。
- 変更によって新しく生じる、または再発し得るリスクは何か。
- 既存テストですでに同じリスクを十分に検証していないか。
- そのリスクを最も直接的かつ安定して検証できるtest levelは何か。

「コードを変更したのでテストも増やす」ではなく、守るべき振る舞いとリスクから必要性を判断する。

## TDD

期待する振る舞いを入出力、状態変化、外部から観測可能な結果として明確に表現できる変更では、TDDを優先する。

基本の流れは次とする。

1. 期待する振る舞いを表すテストを書く。
2. そのテストを実行し、意図した理由で失敗することを確認する。
3. テストを通すための必要最小限の実装を行う。
4. テストが通ることを確認する。
5. 必要なら、振る舞いを変えずに実装やテストを整理する。

Redの段階で実装コードを先回りして書かない。
また、実装を通すためだけにテストの期待値を変更しない。仕様、テスト、実装のどれが誤っているかを判断する。

### TDDを儀式化しない

次のような作業では、TDDの費用対効果が低い場合がある。

- 文書だけの変更
- renameやformat変更などの単純な機械的変更
- まず挙動や実現可能性を調べる必要がある探索的作業
- 自動テストより既存のvalidatorやstatic checkの方が直接検証できる変更

TDDを使わない場合でも、変更後に何をどう検証するかは明確にする。

## 何をテストするか

内部構造ではなく、守るべきbehavior、contract、invariantをテストする。

変更に応じて、次から重要なものを選ぶ。

- 主な正常系
- 重要な境界値
- 利用者に影響する失敗条件
- 過去に壊れた、または今回の変更で壊れやすい振る舞い
- 外部componentとの境界
- Critical User Journey

すべての組合せを網羅することを目標にしない。
故障時の影響と発生可能性を踏まえ、重要なリスクほど厚く検証する。

## Test levelを選ぶ

unit / integration / end-to-endに固定比率を設けない。
守りたい振る舞いを、必要な範囲で最も小さく直接検証できるlevelを選ぶ。

- **unit**: 独立したロジック、変換、validation、局所的なinvariantを高速に検証できる場合。
- **integration**: database、filesystem、network boundary、複数component間の契約など、境界を越えた組合せ自体が重要な場合。
- **end-to-end**: 複数層を通したCritical User Journeyや、下位levelだけでは保証できない重要な経路を確認する場合。

下位levelで十分に保証できる内容を、理由なくE2Eでも重複検証しない。
一方で、重要な境界をmockだけで置き換えて実際のintegrationを一度も確認しない状態も避ける。

可能な限り、高速・決定的・独立して実行できるテストを優先する。

## テスト量を品質指標にしない

テストケース数やcoverage率を品質そのものとして扱わない。

coverageは未検証領域を見つける補助情報として使えるが、数値を上げるためだけのテストは追加しない。
同じリスクを別表現で繰り返し確認するだけのテストも増やさない。

テストコードにも保守コストがある。
追加するテストは、そのコストに見合う不具合検出価値があるかを判断する。

## 脆い・低価値なテストを避ける

次のようなテストは、公開契約や重要な制約でない限り追加しない。

- rename後に旧名称のmoduleをimportしていないことだけを確認するテスト
- private関数の分割方法や内部call sequenceを固定するテスト
- 内部data structureの形だけを固定するテスト
- 順序がcontractでないcollectionの順序を固定するテスト
- 文言がcontractでないlogやerror message全文を固定するテスト
- mockの呼出順序や回数を必要以上に固定するテスト
- 同一の振る舞いを別の表現で繰り返すだけのテスト

実装を別の正しい形へ置き換えても利用者向けbehaviorが同じなら、その変更だけで壊れるテストは再検討する。

## Regression test

バグ修正では、再発時に利用者またはシステムへ実害がある振る舞いを再現できるならregression testを追加する。
可能であれば、修正前に失敗し、修正後に成功することを確認する。

ただし「バグ修正には必ず新しいテストを1件追加する」というルールにはしない。
既存テストがすでに同じcontractを十分に守っている場合や、追加テストが内部実装の存在確認にしかならない場合は、低価値なテストを増やさない。

## 実装後の検証

変更後は次を行う。

1. 変更に直接関係するテストを実行する。
2. repositoryで標準テストが定義されている場合は、それも実行する。
3. 失敗した場合は、期待値を機械的に更新せず、仕様・テスト・実装のどれが誤っているかを確認する。
4. 変更によって意味を失ったテストや重複したテストは削除する。

テストを追加した事実ではなく、変更後の重要な振る舞いを妥当な方法で検証できたことを完了条件とする。

## 他Skillとの関係

- 実装そのものを必要十分に保つ判断は `development-guidelines` を利用する。
- test codeを含むコードの可読性やcomment判断は `readable-code` を利用する。
- 要件や変更範囲そのものの妥当性判断は、このSkillの責務外とする。
