# 日本語技術文書

技術文書では、文章としての面白さより、読者が内容を正しく判断して再利用できることを優先する。
読者が少なくとも次を判別できる状態を目指す。

- 何が決まっているか
- 何が確認済みか
- 何が未確認または推測か
- どの条件や制約の下で成り立つか
- 詳細の正本がどこにあるか

このSkillはrepository非依存の共通原則だけを扱う。
repository固有の用語、文書配置、実行環境、正本の分担、表記規則がある場合は、より具体的なlocal ruleを優先する。

## 優先順位

文書上の判断が競合した場合は、次の順で優先する。

1. 正確性
2. 根拠や正本を追跡できること
3. 用語と説明の一貫性
4. 必要な情報を見つけやすいこと
5. 簡潔さ

短くするために条件、例外、失敗時の扱いを削らない。
一方で、同じ結論や仕様を言い換えて繰り返さない。

## 文書の責務

書き始める前に、その文書が何を正本として持つかを決める。
一つの仕様、設定、手順を複数の文書で独立に保守しない。

別の文書が正本である内容に触れる場合は、その文書で必要な要点だけを示し、詳細は正本へ参照させる。
README、索引、概要文書には、詳細仕様を複製するのではなく入口として必要な情報を置く。

生成物を説明するときは、生成物そのものと、その入力または生成方法のどちらが正本かを区別する。

## 主張の区別

文書中の内容がどの種類の主張かを曖昧にしない。

- 仕様として決めた内容
- 実際に確認した事実
- 計測または観測から得た結果
- 推測や仮説
- 提案または未採用の選択肢
- 前提条件
- 例外
- 制約、上限、失敗条件
- 一部だけを示す例

確認していない内容を断定しない。
一部の環境や入力だけで確認した結果を、一般的な保証として書かない。

上限や打切りがある場合は、値だけでなく到達時の意味を記載する。
例を載せる場合は、その例から保証できない範囲を仕様と誤認させない。

## 用語と識別子

同じ概念には同じ用語を使う。
文章上の変化だけを目的に、定義済みの概念を似た別語へ置き換えない。

分野で一般的な用語がある場合はそれを優先する。
独自用語が必要な場合は初出で意味を定義し、その後は同じ語を使う。

コード上の識別子、API項目名、設定キー、列挙値、コマンド名などの公開名は勝手に翻訳または変更しない。
本文では、公開名を保持したまま役割や意味を日本語で説明する。

## 構成

文書の種類に応じて、読者が必要とする順序で情報を並べる。

| 文書種別 | 最低限追えるようにする内容 |
|---|---|
| API仕様 | 入力、出力、条件、エラー、互換性上の注意 |
| 運用手順 | 前提、実行条件、操作、確認方法、失敗時の扱い |
| 開発手順 | 作業条件、再現可能な手順、検証方法 |
| 技術解説 | 前提知識、対象、仕組み、理由、具体例、制約 |
| チュートリアル | 到達目標、前提、操作、各操作の理由、完了確認 |
| 設計判断 | 背景、制約、選択肢、採用理由、トレードオフ、結果 |

仕様書や手順書では、結論に不要な演出や長い導入を避ける。
解説やチュートリアルでは、理解に必要な背景や具体例を加えてよいが、事実と説明上の例を混同しない。

## 文と段落

一つの文に複数の独立した結論や条件を詰め込まない。
一つの段落では、読者が一つの問いに答えられる程度のまとまりを扱う。

原因と結果を書く場合は、因果関係が根拠から分かるようにする。
「柔軟に」「適切に」「必要に応じて」のような表現だけで条件を省略しない。

文書の進行だけを説明する文は、読者の理解に必要でなければ削る。

## 図、表、コード例

表現形式は、情報の関係を最も誤解なく示せるものを選ぶ。

- 比較や対応関係は表を検討する。
- 時系列、分岐、状態変化は図を検討する。
- コマンド、設定、JSON、HTTPメッセージ、ログ、ファイル構成はコードブロックを使う。

図、表、本文へ同じ情報を重複して書かない。
図表だけでは分からない条件、例外、判断理由を本文で補う。

例示コードは、実際に実行するコードなのか、概念だけを示す疑似例なのかが分かるようにする。

## 推敲

執筆後に次を確認する。

- 文書の責務と正本が明確か。
- 同じ仕様や手順を別の場所へ複製していないか。
- 仕様、確認済み事実、推測、提案を区別しているか。
- 前提、例外、制約、上限、失敗時の扱いを落としていないか。
- 一部の確認結果を一般的な保証として書いていないか。
- 同じ概念へ同じ用語を使っているか。
- 公開された識別子を勝手に翻訳または変更していないか。
- 文書種別に必要な情報が、読者が使う順序で並んでいるか。
- 図、表、本文、コード例が同じ情報を重複していないか。
- repository-localの規則と矛盾していないか。

不要な説明を削るときは、読者が判断するために必要な根拠、条件、例外まで削らない。
